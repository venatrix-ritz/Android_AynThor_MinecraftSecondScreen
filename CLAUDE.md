# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A standalone Android app (Kotlin/Compose) that connects to a companion Fabric mod's loopback socket and renders Minecraft's HUD (health, hunger, XP, armor, hotbar) on the second (bottom) screen of an **AYN Thor** (dual-screen Android handheld), via Android's `Presentation` API. It also sends input back to the mod — tap-to-select hotbar, a button grid for custom keybinds.

This app is one half of a two-process system. The other half — the Fabric mod that hides the vanilla HUD and streams its state — lives in a sibling repo, `AynThorSecondScreen`. The two communicate only via a JSON-over-TCP protocol on `127.0.0.1:48291`; there's no shared code or build.

**`thor-hud-handoff.md`** is a detailed technical handoff/design doc covering the full system (both repos) — read it first for the JSON protocol spec, architecture rationale, and known issues. It's a snapshot from a point in development and its file/class inventory has drifted from the current tree in a few specific ways (see "Handoff doc vs. current code" below) — verify anything file-specific against the actual source before relying on it.

## Commands

```
./gradlew build                  # compile + lint
./gradlew installDebug           # install to a connected device/emulator
./gradlew test                   # JVM unit tests (app/src/test)
./gradlew connectedAndroidTest   # instrumented tests (app/src/androidTest), needs a device/emulator
```

Since the second-screen `Presentation` only appears on real dual-screen hardware, `MainActivity` falls back to a minimal status view on the primary screen when no `DISPLAY_CATEGORY_PRESENTATION` display is found — this is the normal (and only practical) way to dev/test on a regular phone or emulator.

## HUD textures come from the mod, not from bundled assets

**The app needs no Minecraft assets on disk.** On connect, the mod pushes every HUD texture it needs — hearts, armor, food, bubbles, XP bar, hotbar, the bitmap font sheet, the tiled background — as `{"type":"asset"}` lines, resolved through Minecraft's *own* resource manager. That means they already reflect the player's active resource pack, with no pack-parsing, no SAF folder grant, and no hand-copying. `HudAssetCatalog` on the mod side owns the key→path mapping and is authoritative; `HudIcon.assetKey` must match it.

`app/src/main/assets/minecraft/` still exists as a **legacy fallback** (and is gitignored — extracted game textures aren't redistributable and this repo is public). `ResourcePackIconProvider` checks the socket-delivered `assetCache` first and only then a bundled file, so those files are optional and safe to delete; they only matter when running against a mod build older than asset delivery. Note the bundled-path candidate names were partly *guessed wrong* — vanilla nests hearts under `heart/` but keeps armor and food flat with an underscore (`hud/armor_full.png`) — another reason to prefer the mod's copy.

If you do keep local files: **filenames are case-sensitive**, Android's asset manager won't find `Hotbar.webp` when the code asks for `hotbar.webp`, and on Windows a case-only rename can leave the Gradle asset merger reporting a bogus "Duplicate resources" error until `app/build/intermediates/assets` is deleted.

`GameDirectoryAccess` (the SAF folder picker) and `ResourcePackIconProvider`'s `resolveActivePacks`/`searchActivePacksFor` are now **dead weight** — they were the app's own attempt at reading resource packs, which the mod does better. Not yet removed.

## Architecture

Full protocol spec (message shapes, field meanings, command codes) is in `thor-hud-handoff.md` §2 — don't re-derive it from source when the doc already has it verified. In short: the app connects to the mod's socket, receives a full HUD snapshot every client tick (~20/sec), renders it, and can request an item's icon on demand (`ICON:<itemId>` → base64 PNG reply) or send back a short command code representing a simulated key/hotbar press.

**Since that doc was written**, three protocol additions:

- The snapshot gained `air`/`maxAir` (breath in ticks and its current maximum — Respiration raises it above 300) for the bubble row, `absorption` (extra golden-heart health), and `offhand` (a hotbar-slot-shaped object for the off-hand). All parsed with `optInt`/`optDouble`/`optJSONObject` defaults so a newer app still runs against an older mod build; the defaults read as "not drowning, no absorption, no off-hand box".
- Icon replies gained a failure form: `{"type":"icon","itemId":...}` with **no `data` field**, meaning "the mod tried and has no icon for this".
- **`{"type":"asset","assetId":...,"data":...}`** — a HUD texture, pushed unprompted for every catalog key right after a client connects (also `data`-less when unavailable). The `ASSETS` command asks for the bundle again, which is how a resource pack change is picked up — the mod has no reload hook, so nothing re-sends on its own.
- The snapshot also carries **`gameMode`**, **`heartType`** and **`hardcore`**. `HudState.hasStatusBars` applies vanilla's own rule (`ClientPlayerInteractionManager.hasStatusBars()`, i.e. survival or adventure) to hide hearts, hunger, armor, bubbles and the XP bar outside survival-like modes, and `isSpectator` drops the hotbar too. A null `gameMode` (an older mod build) reads as "show them", which is what those builds did. `ui/HeartLayout.heartSprites` picks the heart set on two independent axes — status from the player, hardcore from the world — with absorption hearts following only the hardcore one, which is vanilla's behaviour and easy to get wrong; `HeartSpritesTest` pins it, including unknown types degrading to a plain red heart rather than an empty row.
- **`{"type":"hello","mod":…,"protocol":N}`** — the first line on every connection. Its *absence* is the useful signal: `HudRepository` counts connections that close without one and, after three, sets `portConflict`, which paints a banner naming the problem. A leftover `adb reverse tcp:48291` leaves **adbd** holding the port, and adbd accepts every connection and instantly drops it — from the app that used to be indistinguishable from a flapping connection, so the screen alternated "Not connected" with "Waiting for map data…" and said nothing about the real cause. Note "socket open" no longer means "talking to the mod"; only the hello establishes that.
- **`{"type":"noplayer"}`** — the player is gone (main menu, world unloading, kicked). Sent once on the transition, not repeatedly. The app drops the HUD state, map, container and chat and falls back to each tab's waiting state, but **`isConnected` stays true** — the mod is still running, it just has nothing to report. That distinction is the reason this is a message rather than the mod going quiet: silence is indistinguishable from a stalled game, and the second screen used to sit there displaying a frozen snapshot of wherever you last were.
- **`{"type":"container",…}`** — the open screen handler: `syncId`, `handlerType` (null for the player's own inventory), `title` (also null for the player's own handler — see below), the `cursor` stack, every slot as `{stack, mayPlace, x, y, background?, disabled?}`, the index roles `playerStart`/`hotbarStart`/`armorStart`/`offhandIndex` (the last two -1 for anything but the player's handler), and an optional `progress`. Sent **only when it changes**, plus once per new connection. The reverse direction is **`SLOT:<syncId>,<slotId>,<button>,<ACTION>`**, where `ACTION` is a `SlotActionType` name (`PICKUP`, `QUICK_MOVE`, …) and slot **-999** means "outside the window", i.e. drop. The `syncId` is echoed back as a staleness check, and the mod refuses the click if the open handler has changed underneath.
  - **`x`/`y` are vanilla's own GUI coordinates** for the slot's 16x16 item area, straight off `Slot`'s public fields — the 18x18 cell starts one pixel up and to the left. This is what `ui/ContainerLayout` draws every container's shape from, and it removed the need for any per-container-type table; `-1` means a mod build predating them, which falls back to the old 9-wide strip. `background` is `Slot.getBackgroundSprite()`, vanilla's empty-slot placeholder, resolved through `ResourcePackIconProvider.getSpriteBitmap`. `disabled` is sent inverted and **only when true** — "enabled" is the default and spending a field on all 46 slots to say it would be the expensive encoding.
  - **`title` is deliberately null for the player's own handler** rather than "Inventory". That handler is current both with the inventory screen open and with no screen at all, so taking the screen's title would flip it null → "Inventory" → null on every tap of E, re-broadcasting 46 slots for a header that never changed. `InventoryScreen` labels that case itself.
  - **`progress` is quantised to drawn pixels, not raw** (`cookPixels` 0..24, `litPixels` 0..14, `fuelPixels` 0..18, `brewPixels` 0..28, `brewing`). A raw `getCookProgress()` changes every tick, and this message is broadcast on change — a smelting furnace would have put it back to 20 broadcasts a second of 46 slots each. Pixels collapse that to the visibly distinct frames and lose nothing, since a pixel is the finest difference the app could draw. Null fields mean "this container has no such indicator", which is different from zero. The brewing **bubble phase is not sent**: it cycles every 14 ticks and carries no information, so `ui/ContainerDecorations` animates it from the frame clock — the same split as the enchant glint.
- **`{"type":"chat","segments":[{"text":…,"color":…},…]}`** — one chat line, as coloured runs. Pushed live, and replayed as a backlog (the last 100, vanilla's `ChatHud` cap) to each new connection right after the bindings — so restarting the app mid-session doesn't lose the conversation. `color` is RGB and is **omitted** for default-coloured text. Colour is the only styling that survives the mod's flattening of Minecraft's `Text` tree; bold/italic/obfuscated are dropped, since this app draws from a bitmap font sheet where each would need its own draw pass. The reverse direction is **`CHAT:<message>`**, which the mod normalises and splits on a leading `/` exactly as the game's own chat box does.
- **`{"type":"bindings","bindings":[{id,label,category,boundKey,unbound},…]}`** — every key binding the game has, pushed straight after the asset bundle and re-sent on a `BINDINGS` request. Always the whole list, never a delta. `id` is the binding's translation key and the only part that's a contract: it's what an input-grid slot persists and what `BIND:<id>` sends back. The display fields are translated mod-side because only the game has the language files, and `boundKey`/`unbound` are a **snapshot** — a mid-session rebind pushes nothing, so the app re-requests when the picker opens. Ids never go stale, so buttons keep working even when the printed key name lags.

**Why the app is standalone rather than a launcher fork:** Android's `Presentation` API (`DISPLAY_CATEGORY_PRESENTATION`) is available to any app, so no ZL2-side integration is needed. "Only show the second screen when the mod is running" falls directly out of socket-connection state, with no separate detection logic.

### Key classes (`app/src/main/java/com/exojosh/minecraftsecondscreen/`)

- `MainActivity` — finds the Thor's presentation-category external display via `DisplayManager`; owns the single `HudRepository` instance; shows `SecondScreenPresentation` there if found.
- `SecondScreenPresentation` — `Presentation` subclass hosting a `ComposeView`, with lifecycle/viewmodel/saved-state owners manually wired to the host `Activity` (required because a `Presentation`'s window sits outside the normal Activity view hierarchy).
- `net/HudRepository` — owns the reconnect loop to the mod's socket (`net/ReconnectPolicy`: five fast 1.5s retries, then backoff to a 30s cap — fast where it matters, a game restart, and patient only for a sustained outage. Reset by the mod's *hello*, not by a socket opening, since against a port squatter "connected" isn't success), parses inbound lines by presence/absence of `"type":"icon"`, exposes `hudState`/`isConnected`/`mapTile`/`bindings`/`chatMessages` as `StateFlow` and `iconCache` as an unbounded Compose-observable map, and has `sendCommand()`/`requestIcon()`/`sendBinding()`/`requestBindings()`/`sendChat()` for the reverse direction. `bindings` is deliberately **not** cleared on disconnect, for the same reason `assetCache` isn't: the mod re-sends the whole list on reconnect, so keeping the old copy stops the input grid flashing back to raw ids through a game restart. `chatMessages` **is** cleared, for the same underlying reason pointed the other way — the mod replays its whole backlog to each new connection, so keeping the old copy wouldn't preserve anything, it would duplicate everything the backlog repeats. `sendChat()` flattens newlines, because the protocol is newline-delimited and a message containing one would reach the mod as two commands. Icons arriving from the mod are rendered isometrically by the mod itself (see its CLAUDE.md), so nothing here needs to know about item models.
  - **Icon request retry:** `requestIcon()` is called during composition, so it must tolerate being hit every frame. It tracks `pendingIconRequests` (itemId → timestamp) and `failedIconRequests` rather than a plain "already requested" set. The set version was a real bug: a request that was never answered — because the mod couldn't resolve the item, or because it was sent before the socket came up and `sendCommand()` dropped it — permanently blocked that item from ever being requested again, which is what made icons appear inconsistently. Requests now expire after `ICON_REQUEST_TIMEOUT_MS` and retry; an explicit "no icon" reply from the mod (a `"type":"icon"` line with no `data` field) backs off for `ICON_FAILURE_RETRY_MS` instead of retrying hot; and both maps clear on disconnect so a reconnect re-asks immediately. `requestIcon()` also refuses to mark anything pending while `writer == null`.
- `net/GameDirectoryAccess` — SAF folder-picker + persisted URI permission, granting read access to ZL2's game directory (must point at shared storage, not `Android/data/...`, which is cross-app-inaccessible on Android).
- `net/ResourcePackIconProvider.getSpriteBitmap(spriteId)` — **the one texture lookup with no `HudIcon` entry, on purpose.** Every other sprite is one this app decided it wanted, so naming it in the enum is right. Slot placeholders and progress art are named by the *game*, at runtime: the mod reports whatever `Slot.getBackgroundSprite()` returned, and an enum can only list what someone thought to enumerate. So a sprite id is converted to a catalog key by the same mechanical rule the mod registered it under (`HudAssetCatalog.putSprite`: path with the slashes flattened), and a sprite the catalog doesn't serve — a modded container's own placeholder — resolves to null and draws no ghost. Appearance, not function, same as every other missing texture here.
- `net/ResourcePackIconProvider` — resolves HUD sprite icons (hearts/armor/food/xp) from the active resource pack (parses `options.txt` for pack order, searches zip/folder packs by the `HudIcon` enum's candidate paths), falling back to bundled assets under `app/src/main/assets/` when a pack doesn't override a sprite — the bundled-fallback logic lives inside this file, not a separate provider class.
- `settings/HudSettings` — which HUD elements are on screen, persisted in `SharedPreferences` (not DataStore: seven booleans read at startup and written on a tap don't justify the dependency). The live copy is a `mutableStateMapOf`, so a switch flip recomposes the HUD immediately — same trick as `HudRepository.assetCache`. Everything defaults to visible, so a fresh install looks like it did before the setting existed. `HudElement.key` is the persisted string: rename the constant, never the key, or you silently reset that toggle for everyone who had it off.
  - **Switching an element off moves it to the top screen, it doesn't lose it.** `SecondScreenApp` pushes the off-set to the mod (`HudRepository.sendGameHudElements` → `HUD:<key>,…`) and the mod re-enables the matching vanilla HUD element, so between the two displays the HUD is drawn exactly once. Full state every time, not deltas, re-sent on each toggle and each reconnect — a dropped delta would have the screens disagree about who owns an element. `HudElement.key` is therefore both the persisted preference name and the wire name; renaming one breaks both. `offhand` is the one key with no mod-side counterpart, since vanilla draws that box as part of the hotbar.
- `settings/InputSettings` + `settings/InputSlotCodec` — which key binding each of the Input tab's 9 buttons presses, persisted in `SharedPreferences`. **Slots hold a binding *id*, not a key name or a label**, so a button follows the action when the player rebinds it in game — which is what "put Drop on the second screen" actually meant. `null` is a real state (an empty slot), and the grid stays a fixed 3×3 rather than compacting, because these are thumb targets and muscle memory beats filling the gap. The persisted format is one comma-joined string under one key: a *missing* string means "never configured" → defaults, an all-empty one means "configured, everything cleared" and must survive a restart. That distinction plus the pad/truncate behaviour is why the codec is **Android- and Compose-free and unit tested** (`InputSlotCodecTest`) — same line as `HeartLayout`; this is persistence code, so a bug here doesn't crash, it silently hands the player a different grid.
- `ui/SettingsScreen` — the HUD toggle list, the chat-keyboard toggle *and* the input-button list, in the Settings tab's panel.
  - **The binding picker replaces the panel's content rather than opening a `Dialog`.** A Compose `Dialog` creates its own window, and this whole tree lives inside a `Presentation` whose window already sits outside the Activity hierarchy; swapping the content keeps one window and one lifecycle with nothing extra to wire. It re-requests the binding list on open, since a rebind in game pushes nothing. **Visibility only, deliberately, not drag-to-place**: every status row lays out on the shared `STATUS_ICON_SIZE`/`STATUS_ICON_COUNT` grid, and free placement would either break that invariant or need a layout engine to preserve it. Granularity is per *element* rather than per row even where two share a row (armor/breath, health/hunger) — armor is always-on and static while bubbles only show when they matter, which is exactly the pair someone would want to split.
- `SecondScreenApp` — the screen's frame, shown inside the `Presentation`. Lives directly under the `minecraftsecondscreen` package, not `ui/`. **Tabs do not swap the whole screen**: the status stack (`HudScreen`) is always on top, and a tab only chooses what fills the panel *below the hotbar* — the map on the HUD tab, the chat log on the Chat tab, the button grid on the Input tab. That's the point of the second screen: vital signs stay visible while the rest of the space does something else. Adding a tab is one `SecondScreenTab` entry plus one `when` branch; the strip is generated from the enum, so don't hand-write another Button. The strip's buttons are `MinecraftButton`s at equal weights — the selected tab draws the *highlighted* (hover) sprite, since vanilla has no sticky selected state but that sprite is exactly the "this is the one you're on" treatment, and inventing a colour would have left the only Material-looking thing on the screen. This also provides `LocalMinecraftGui` for the whole window, and owns the tiled backdrop — nothing nested inside should paint its own full-size background, or the dirt gets drawn twice.
- `ui/HudScreen` — the status stack: armor/bubbles, hearts+hunger, XP bar, hotbar. Each is gated on `HudSettings`. **Wraps its own height** and paints no background, because the panel below it takes the remaining space via `weight(1f)`.
  - **The armor sockets are hidden at zero armor, but their row's height is not.** Vanilla wraps `renderArmor` in `if (j > 0)`, so drawing empty sockets showed something the top screen never would — but this stack is top-anchored where vanilla's HUD is bottom-anchored, so collapsing the row would jump the hearts, XP bar, hotbar and map up the screen every time a chestplate came off. Gate the icons, keep the row.
  - **The armor/bubbles row is pinned to `STATUS_ICON_SIZE` rather than sized by its children.** Its height used to come from the armor icons, which made armor quietly load-bearing for the whole layout — harmless while armor was always drawn, but once it became switchable the row would collapse and re-expand every time the player surfaced, dragging everything below it up and down. For the same reason both status rows use an explicit `Spacer(weight(1f))` instead of relying on `Arrangement.SpaceBetween`: with one child hidden, SpaceBetween pushes the survivor to the *start*, sliding the bubbles or hunger row over to the left edge. `XpBar` and `BubbleRow` both work in *logical texture pixels* scaled from the available width, the same approach `HotbarRow` uses — see below. Also defines `RepeatingTextureBackground`, the tiling helper (inline in this file, not a separate file).
- `ui/MapScreen` — the live map, in the HUD tab's lower panel. The tile arrives already coloured with vanilla's map palette, so this only scales it (whole-pixel, `FilterQuality.None`) and draws the player marker. The marker is placed from the tile's own `originX`/`originZ`, which the mod sends precisely so this side doesn't reimplement `MapRenderer`'s centring and then drift from it.
  - **The tile sits on vanilla's `map_background.png` paper sheet**, at vanilla's own proportions: `HeldItemRenderer` draws that sprite from -7 to 135 while the map data covers 0 to 128, so the border is 7 map pixels a side and the sheet is 142 across. The fit is computed against the 142 footprint, not the 128 map, so the *sheet* is what's sized to the panel. The paper is the one thing here deliberately **not** on whole pixels — it's a 64×64 sprite stretched to 142, exactly as vanilla stretches it, and it's a soft gradient with no pixel grid to preserve. It's also load-bearing rather than decorative: unloaded-chunk pixels arrive fully transparent, and on paper they read as unexplored map instead of as a hole showing the dirt backdrop.
  - **Whole-pixel scaling makes panel space unusually valuable here.** The map is height-bound and quantised, so a few dp of inset can cost an entire integer step of map size. That's why this composable has no padding and why `TAB_STRIP_HEIGHT` is kept tight — don't add margins back without checking what step it lands on.
  - `XpBar` follows `ExperienceBar.renderBar`: the 182×5 progress sprite is **source-cropped** to the fill fraction and drawn into the same fraction of the destination, keeping it at 1:1 scale so its internal segment boundaries line up with the unfilled bar behind it. Don't reimplement this as a full-width `Image` inside a clipped/`fillMaxWidth(fraction)` box — `Modifier.width()` is only a *preferred* size, so the narrowed parent constraints squeeze the Image and `ContentScale.FillBounds` stretches the bitmap. That was a real bug; the explicit `drawImage(srcOffset/srcSize/dstSize)` form is there to avoid it. Vanilla's fill width is `progress * 183` (one wider than the sprite, so a nearly-full bar actually reaches the end); that's preserved and clamped. The level number is `MinecraftTextStyle.OUTLINE` in `#80FF20`, hidden at level 0, and deliberately overhangs the bar upwards with its bottom 2px overlapping — all straight from `Bar.drawExperienceLevel`.
  - `HeartRow` follows `renderHealthBar`, including absorption: `ceil(maxHealth/2)` normal slots followed by `ceil(absorption/2)` absorption slots in one continuous run, every slot backed by a container, and the last absorption heart drawn as a half when the amount is odd. It wraps into stacked rows every 10 the way vanilla does, rows growing *upward*. **The slot maths lives in `ui/HeartLayout.kt`, deliberately free of Compose and Android types so it can be unit-tested** — that separation is not incidental tidying. The previous version clamped the run to 10 slots, which meant a normal-max-health player (already 10 slots) could never show an absorption heart at all: the feature was unreachable code and shipped that way, because nothing tested it. `HeartLayoutTest` pins the boundaries; keep new layout maths on that side of the line.
  - **The bubble index is deliberately mirrored.** Vanilla positions bubble `n` (1-based) at `left - (n-1)*8 - 9`, so n=1 is the *rightmost* and full bubbles are `n <= k`. As air drops the highest-numbered bubble goes first, so the row empties from its **left** end. Laying bubbles out in naive left-to-right index order pops them from the wrong side; `position = STATUS_ICON_COUNT - index` is what fixes it.
  - **All four status rows (armor, hearts, hunger, bubbles) share the `STATUS_ICON_SIZE`/`STATUS_ICON_COUNT` grid.** Vanilla aligns its rows for free because they all use 9px sprites on an 8px pitch; this HUD draws icons edge to edge instead, so anything not on that shared grid comes out a different width than the row above it. Bubbles previously used vanilla's 8px pitch and ended up narrower than the hunger row.
  - `BubbleRow` follows `InGameHud.renderAirBubbles`. Bubble counts use vanilla's `getAirBubbles` rounding, where the full count lags two ticks of air behind so the last bubble visibly bursts before vanishing. Only rendered while `air < maxAir`, matching vanilla (there's no full-row idle state). Vanilla's brief `air_empty` pop animation isn't reproduced, so an emptied slot renders nothing — same class of simplification as the enchant glint. It shares a `Row` with the armor icons rather than having its own line, mirroring vanilla's stacking: armor above health on the left, bubbles above hunger on the right. The row's height comes from the armor icons, so it doesn't collapse when the player surfaces.
- `ui/MinecraftFont` — vanilla in-game text. Minecraft's font is a **bitmap sheet, not a TTF**, so matching it means drawing glyphs from `assets/minecraft/textures/font/ascii.png` (a 16×16 grid of cells covering codepoints 0x00–0xFF) rather than shipping a lookalike font file — which also means a resource pack restyling the font works automatically. `MinecraftFontSheet.from()` measures each glyph's advance the way vanilla does (scan the cell right-to-left for the last column with any non-transparent pixel, +1px letter spacing), normalising to vanilla's 8-logical-pixels-per-cell so a hi-res pack sheet lays out identically to the 128×128 default; space is hardcoded to 4 since it has no pixels to measure. `MinecraftText()` draws it with vanilla's 1px offset quarter-brightness drop shadow. Build the sheet via `rememberMinecraftFont()` — measuring walks every pixel, so don't redo it per recomposition. Sizing is in *font pixels* (`pixelSize`), not `sp`.
- `ui/HotbarRow` — the 9 hotbar slots: on-demand icon request, stack count, durability bar, static enchant-glint overlay, selected-slot highlight, tap-to-select.
  - **The off-hand box is on its own line under the strip, flush right, and is not vanilla-faithful on purpose.** Vanilla hangs it off the side of the hotbar at the same height; putting it there would steal horizontal space from the strip (182 → 211 logical px, shrinking every slot). On a touch screen the hotbar wants the full width and the off-hand wants to be under a thumb, so it gets its own row. It uses the **right** variant sprite (`hotbar_offhand_right`) because that sprite's 8 blank spacer columns fall on its left — right-aligning the left variant would inset the cell from the screen edge by those 8 columns. Geometry (29×24, cell at (8,2), icon at (10,4)) was measured out of the 1.21.11 client jar, not recalled.
  - **On the HUD tab that extra line costs no layout height** (`offhandOverflowsBelow` → `Modifier.hangingBelow`, which measures and places the box at full size but reports height 0). The box is 29 of the hotbar's 182 logical pixels, hard right, so charging a whole row for it wasted a wide band either side — the map gets that row back and the box floats over it. Compose neither clips the overflow nor lets the panel steal the box's taps, since `MapScreen` draws nothing there and has no pointer input. The map sheet is square, centred and height-bound, so at any normal HUD height it stays well clear of that corner — but `SecondScreenApp` still gives the status stack `zIndex(1f)`, because the failure mode if they ever did overlap is an invisible tap target under the map, which is worse than either of them simply drawing on top. Input and Settings pass `false` — their content runs the full width (the grid's top-right button, Settings' "Reset") and would be covered.
  - It also stays on screen when the off-hand is **empty**, which vanilla doesn't do, because tapping it is the only way to put something *into* the off-hand from the second screen. `offhandSlot == null` (an older mod build that doesn't send the field) hides it; an empty off-hand arrives as a `minecraft:air` slot and still draws.
  - Takes optional `backgroundBitmap`/`selectionBitmap` params (sourced from `HudIcon.HOTBAR_BACKGROUND`/`HOTBAR_SELECTION`); when null it falls back to the original per-slot bordered boxes. No actual hotbar texture is bundled yet — drop one into `app/src/main/assets/minecraft/textures/gui/sprites/hud/hotbar.png` (and optionally `hotbar_selection.png`) to activate it. The pixel-alignment math is a best-effort approximation of vanilla's proportions (182x22 background, 20px slot pitch, ~24px-wide selection overlay), scaled from whatever bitmap actually gets bundled rather than hardcoded pixel counts — check it visually on-device once a real texture is in place, per the note in `thor-hud-handoff.md` on hotbar pixel alignment.
- `ui/ChatScreen` — the Chat tab: the game's chat log, and a keyboard to answer it with. The log renders through `MinecraftTextLines` (Minecraft's own bitmap font, so a resource pack restyling it applies here too), which means it carries the same 0x00–0xFF limit as every other piece of text on this screen — anything outside draws as `?`. A null font sheet falls back to plain Compose text rather than a blank panel.
  - **The log is a `reverseLayout` list whose "follow the tail" flag is only recomputed when a scroll *gesture* ends.** Both halves are load-bearing and neither is the obvious version. Scrolling to the last item "if already at the bottom" broke the moment the keyboard opened: that shrinks the viewport, leaving the list showing its top with items below, so "at the bottom" read false forever and messages stopped appearing. Reversed, the newest message is index 0 — but a `LazyColumn` re-anchors onto whatever item was first visible when the list changes, so inserting at index 0 moves the anchor to index 1 and *any* check made after an insert reports "scrolled away". Inserts don't start a scroll, so gating on `isScrollInProgress` reads only real gestures. Both bugs looked fine in every state except the one that matters.
  - **`ChatDraftState` is hoisted to `SecondScreenApp`**, because tabs swap the panel's content outright and a draft owned by `ChatScreen` would be lost by glancing at the map mid-sentence.
  - The draft bar has **no Send button of its own** — the keyboard has one, and a draft can only be typed with the keyboard open. It used to have one and it was worse than nothing: disabled-grey over the dirt background, it read as a control that had failed to load.
- `settings/ChatSettings` — one boolean, `useSystemKeyboard`, same `SharedPreferences`-and-Compose-state shape as `HudSettings`. **Off by default**, because the app-drawn keyboard exists for a real reason (see `ui/ChatKeyboard`). The switch exists because that reason is a property of the *device*: where the system keyboard does come up on the bottom screen it's far nicer to type on, and only the person holding the Thor can see which happens. When it's on, `ChatScreen`'s draft line becomes a real text field (an IME needs an input connection; the bitmap-font line is a `Canvas` and has none) with Send on the keyboard itself, and `SecondScreenPresentation` sets `SOFT_INPUT_ADJUST_RESIZE`.
  - **That field is a platform `EditText` in an `AndroidView`, not a `BasicTextField`, and swapping it back would break the feature.** Compose exposes no way to set `IME_FLAG_NO_FULLSCREEN`/`IME_FLAG_NO_EXTRACT_UI`, and without them an IME in landscape enters *extract mode*: it replaces the whole display with its own full-screen editor. Verified on the Thor — tapping the draft line wiped the HUD, the log and the tab strip off the bottom screen and left a blank white sheet with a caret. With the flags set, Gboard docks over the panel and everything stays visible and typable.
  - On this device the IME does come up on the **bottom** screen, and it floats over the panel rather than resizing it (a presentation display doesn't report IME insets, so `imePadding()` is a no-op there) — the draft line still sits clear of the keyboard, so this is left alone.
- `ui/ChatKeyboard` — an on-screen keyboard this app draws, **not** Android's IME, and that is the design rather than a reinvention. Android only shows an IME on a secondary display when that display reports system-decoration support, which presentation-category displays generally don't; where it does appear it appears on the *primary* screen, which on this device is the one running Minecraft — the keyboard would cover the game while the field it types into sits on the other panel. Drawing our own also lets the layout be the one a game needs: `/`, `~`, `^`, `@`, `:` and `{}` are one tap away. The symbol layer is a deliberate subset (`# $ % & * + < > \ |` have no key); a fifth row costs more panel height than they're worth.
- `ui/ChatLineWrapper` — word wrapping for the log. **Free of Compose and Android types and unit tested** (`ChatLineWrapperTest`), same line as `HeartLayout` and `InputSlotCodec`: widths come in as font pixels and advances as a function, so it never sees a `Dp` or a bitmap. Wraps by character rather than by run, because a single coloured run can be longer than a line and colour boundaries have nothing to do with where a line should break. This is exactly the kind of code that fails silently — a bad break loses characters or spins rather than crashing.
- `ui/InventoryScreen` — the Items tab: the open screen handler, with tap and drag to move items, drawn on the game's own container panel (`Modifier.vanillaPanel()` and `vanillaSlot()` from `ui/MinecraftGui`). **Nothing is applied optimistically** — every interaction goes back as a `SLOT:` click and the resulting state comes from the game, so what's drawn is always what the server thinks is true.
  - **Hit testing is rect containment over the placed cells, on one gesture handler.** It used to be row/column arithmetic, which no longer describes anything — a container's cells are wherever vanilla puts them and a furnace's three are not on any grid. What stayed load-bearing is the *one handler*: giving each cell its own pointer input would make a drag stop existing the moment the finger left the cell it started in, which is the entire gesture. Both regions are covered by it, so a drag out of a furnace's output into the hotbar is one gesture.
  - **The whole panel is drawn in texture pixels scaled by a single unit**, floored to a whole device pixel. The slot sprite's bevel is one texture pixel wide, and at a fractional scale it lands two device pixels wide on some cells and one on others, which reads as a rendering fault rather than as a smaller inventory. One unit for the cells, the group gaps and vanilla's progress art is also what stops those three drifting apart.
  - The control bar's centre text is **"Holding" → the container's title → the spread-gesture hint**, in that precedence. The title only appears here; with every block now drawn in its own shape, saying *which* block reads as the caption to that shape. The hint loses least by being last — its job is discovery, and the case where it still shows (the player's own inventory, which has no title) is where a new player starts.
  - **Amount is a mode, not a gesture** (`Stack`/`Half`/`Single`, plus `Move` for shift-click). Long-press and multi-touch are the obvious mappings for the amounts, but they have to be raced against the drag detector, and losing that race silently performs the *wrong move* on a real inventory.
  - **The mode governs the drag, not just the tap.** Every drag used to be a plain two-step `PICKUP` regardless, so picking "Half" and dragging still moved the whole stack and the buttons looked like they did nothing. The sequences now live in `ui/InventoryMoves` — see there; releasing off the grid or on the source re-clicks the *source*, putting the stack back, since a slipped finger did not mean "drop this on the floor".
  - **Hold still, then drag, to spread a stack across slots** — vanilla's own drag, sent as a `QUICK_CRAFT` sequence. This is the one hidden gesture on the screen and it's advertised in grey text in the control bar. It's affordable where a hidden half-click wasn't: it doesn't do the *wrong* move, it builds a visible painted set the player can watch before lifting. The hold is measured with **`AwaitPointerEventScope`'s own `withTimeoutOrNull`**, not `kotlinx.coroutines`' — the pointer-input frame clock is what makes the hold measurable from a test's virtual clock, and the coroutines one compiles fine while quietly breaking the instrumented test.
  - The cursor readout ("Holding") is not decoration: a half-finished move is otherwise invisible, and the player is left wondering where their diamonds went. `Drop` sends slot **-999**, vanilla's "clicked outside the window".
- `ui/InventoryMoves` — every gesture's click sequence, as vanilla clicks. **Compose- and Android-free and unit tested** (`InventoryMovesTest`), same line as `InventoryLayout`/`HeartLayout`/`InputSlotCodec`/`ChatLineWrapper` and for a sharpened version of the same reason: a wrong sequence here doesn't crash, it moves a different number of items than the player asked for, on a live world.
  - **No vanilla click picks up exactly one item**, so `Single` is the mirror of `Half` rather than its twin: `Half` takes half (right click) and places all of it, `Single` takes the whole stack and places one at a time. A single-item *drag* is therefore three clicks — lift, right-click one in, left-click the source to return the remainder — and that third click is skipped when the target holds a **different** item, because a right click there swaps rather than places and "give the rest back" after a swap would scatter both stacks.
  - The distribute drag follows `HandledScreen.mouseReleased` exactly: stage 0 outside the window, one stage-1 click per painted slot, stage 2 to commit, with the stage and mouse button packed by `ScreenHandler.packQuickCraftData` (stage in the low two bits, button in the next two). Nothing is sent while the finger moves. The cursor **must** already hold the stack or the server abandons the drag at its first click, which is why the source is picked up first. Button 0 is the even split, 1 is one-item-per-slot (`Single`); button 2, the creative full-stack drag, is never sent.
  - This is the one tab that **hides the status stack** (`SecondScreenTab.showsStatusStack`) — six rows of slots don't fit under the HUD, and the inventory is looked at deliberately rather than glanced at.
- `ui/ContainerLayout` — slots → placed cells on a texture-pixel canvas. **Compose- and Android-free and unit tested** (`ContainerLayoutTest`), same line as the rest, because a wrong position here doesn't crash: it puts a cell where the finger isn't, or worse, where it *is* but belonging to a different slot.
  - **The container's shape comes from the game, and there is no per-type table on either side.** Every non-player container used to be a 9-wide grid of its slots — chest-shaped, and nothing else is. A crafting table came out as a strip of nine with the result wrapped onto a phantom second row; a brewing stand as five identical cells; a furnace, grindstone, anvil and smithing table as anonymous squares in a row with no indication which was the output. Adding a layout table per type would only ever cover what someone enumerated and would drop modded containers back onto the strip. `Slot.x`/`Slot.y` are public and hold the coordinates the game draws at, so the mod ships them and this places them: a furnace's input lands above its fuel with the output to the side because that is where the handler put them.
  - **Vanilla's `x`/`y` are the top-left of the 16x16 item area, not the 18x18 cell** — hence the `-1`. Off by one there misaligns every cell against its own bevel, and against the decorations by two.
  - **The player's 36 slots deliberately keep `InventoryLayout`'s rows** instead of also being placed by coordinate. Vanilla puts them at a fixed y with ~13px of dead space above, sized for a mouse in a 176x166 window; stacking them straight under a compactly-placed container region is why a furnace's three slots come out large here and small in game. The two regions share one cell size, and the narrower is centred over the wider — a furnace's region is 78px against the player's 162, and left-aligning it would hang the container off one edge.
  - Cells sit **edge to edge on vanilla's 18px pitch**, not on the old 2dp gap. The slot sprite's own bevel is the separator vanilla relies on; adding a second one was inventing a metric, and mixing it with the container region's vanilla pitch would have made the two regions disagree.
- `ui/ContainerExtrasPanel` (`ContainerExtrasBand`) — the controls for a container whose function isn't its slots: an enchanting table's three offers, a stonecutter's recipes, a loom's patterns, a villager's trades, a beacon's effect pair, an anvil's rename. Slot geometry made those legible; it did nothing for the fact that their actual function is a *choice*, so they were drawable but dead.
  - **A band across the top, not a column beside the grid.** The first version split the width roughly in half, and that was the wrong axis to spend: the slot plan is at most 162 texture pixels wide and its cell size is bound by whichever axis runs out first, so halving the width halved the cells — a small grid sitting inside wide empty margins, while short lists had far more room than they needed. Across the top, every list runs horizontally and scrolls, the band takes only the height its content wants, and the grid gets the entire width. The beacon is the one container that genuinely needs two rows, which is why the band wraps its height rather than fixing it.
  - **The villager is the one exception, and it's a shape argument** (`ContainerExtras.prefersSideRail`). Every other container's choice is a *row* of things, which reads as a horizontal strip; a trade is itself three stacks laid left to right, so a list of trades is a list of rows, and rows stack downwards. Turned sideways each trade became a wide card, only three or four fitted, and the whole thing read as a clump of tiny slots. Stacked in a rail they all fit and each reads the way it does in game. The rail is a **fixed narrow width** (`SIDE_RAIL_WIDTH`), not a weight — one trade is three cells across and that is all it ever needs to be; a weight is what made the original side-by-side layout cost the grid so much. An absent second cost still holds its place, so the result column stays aligned down the rail.
  - **The beacon's effects are the game's own icons**, from `textures/mob_effect/` via `ResourcePackIconProvider.getStatusEffectIcon`. They were text buttons — a row reading "Speed Haste Resistance Jump Boost Strength" that was mostly words and looked nothing like the game's picker. A locked effect keeps its icon dimmed with the beacon level it needs in the corner, where a stack count would go. "Amplify" borrows the chosen primary's icon, since that's literally what it is, and falls back to a text button before a primary is picked. Only the six effects a beacon can offer are served, so anything else degrades to the text button rather than an empty cell.
  - **Every control is built from `MinecraftButton`, `vanillaSlot()` and `MinecraftText`, and that's why this tier needed no new textures.** Vanilla has bespoke sprites for each of these lists (`container/stonecutter/recipe`, `container/enchanting_table/level_1`, `container/beacon/button`); using them would have meant ~25 more assets to reproduce widgets the app already draws in the game's own style, for information the item icon and label already carry. Stonecutter and villager icons come through the existing `ICON:` path, so real items with no new machinery.
  - **The beacon holds a pending pair and sends on Apply.** `UpdateBeaconC2SPacket` carries both effects together, so sending per tap would clear the secondary the moment the player touched the primary. "Amplify" is vanilla's second secondary option and is the primary's own id in both slots, which is why the mod doesn't list it as an effect.
  - **The anvil's keyboard is not part of the band.** It used to be pinned open underneath, costing four rows of height permanently — for a control touched once per repair — which left the grid with half a screen. The field sits in the band and `ChatKeyboard` appears below it only while typing. Still the app's own keyboard rather than an IME, for the reason that component exists. The name goes out as it's typed rather than on a confirm, because the *price* depends on it and that's what the player needs to see; vanilla does the same.
  - Locked and unavailable rows are **disabled, not hidden**: "you need 3 more levels" or "needs beacon level 4" is the answer the player opened the block for, and an omitted row just looks like the block is broken.
  - **Labels are ASCII only.** The bitmap font sheet covers 0x00–0xFF and anything outside draws as `?` or as the wrong glyph — a `·` separator came out as garbage and a `→` as a literal question mark. Use `-` and `>`.
  - **Nothing here formats an enchantment level.** `Enchantment.getName(entry, level)` already returns "Sharpness II", numeral included; appending one printed "Sharpness II II".
  - A selected recipe is marked with `Modifier.vanillaSlotHighlight()` — a **border**, not `SlotOverlay`'s wash. A 50%-white wash over a full cell obliterated the icon, so the one cell telling the player what they'd picked was the one they couldn't read.
- `net/ContainerCommands` — the wire form of every container command that isn't a slot click. **Android-free and unit tested** (`ContainerCommandsTest`), same line as `InputSlotCodec`/`ContainerLayout`, for the sharpest version of the reason: these strings are all the mod sees, and a wrong one enchants a different row, selects a different trade, or clears a beacon the player just set, on a live world, while looking like the button did nothing. Two traps are pinned by tests — a null beacon effect must be the `-` sentinel and never an empty field (`BEACON:1,,` is indistinguishable from a deliberate clear), and a rename must keep commas (the mod splits that one command on its *first* comma only, since an item name is arbitrary text) while flattening newlines (the protocol is newline-delimited).
- `ui/ContainerDecorations` — the furnace flame/arrow and brewing bar/arrow/bubbles, positioned in vanilla's coordinates via `ContainerPlan.decorationOffsetX/Y`. Unlike slot positions, a progress indicator's position is drawn by a vanilla `Screen` subclass and exists nowhere the mod can read generically — so this **is** a small closed table, of the two families that have any, with the offsets transcribed from the 1.21.11 screens. Partly-filled bars are **source-cropped** to the filled pixels and drawn into the same count, never the whole sprite squeezed (the trap `XpBar` documents), and the crop is expressed against each sprite's *logical* size so a 2x resource pack still comes out the right shape. A layout that didn't come from vanilla's coordinates has nowhere correct to put these, which `positionedByVanilla` gates.
- `ui/InventoryLayout` — slot indices → rows on a 9-wide grid. **Compose- and Android-free and unit tested** (`InventoryLayoutTest`), same line as `HeartLayout`/`InputSlotCodec`/`ChatLineWrapper`, because a wrong index here doesn't crash — it clicks the wrong slot, and on a live world that moves an item somewhere the player never asked. The tests immediately earned it: slot 45 (off-hand) is *after* the hotbar in the player's handler, so `hotbarStart until size` swallowed it and drew it twice, once in the equipment row and again as a stray tenth hotbar cell wrapping onto a phantom second row. **Now the *player's* half only** — `playerRows()` is what `ContainerLayout` composes; `compute()` is kept for the row-form description and the index tests.
- `ui/InventoryScreenTest` (androidTest) — the drag itself, exercised by dragging: the two-click move, half/single mode drags, the hold-then-drag spread, and the off-grid release. The slot maths is pinned in JVM tests, but "a finger moved from here to there" → "these two clicks were sent" only exists inside a real Compose pointer pipeline. **Both layout shapes are exercised**, because they're different problems: the player's inventory is one regular grid, a container is scattered cells with real dead space between them. The furnace cases cover a drag from its output into the player's rows (one gesture crossing both regions) and a tap in the arrow's gap doing *nothing* — snapping that to the nearest cell would make the output a far bigger target than it looks, and on a furnace the neighbouring target is "take the smelted item". It's also the only way to check this UI on the Thor when the AYN assistant panel is sitting over the `Presentation`, since it renders in the activity's own window on the primary display.
- `ui/CreativeScreenTest` (androidTest) — the creative picker's long-press-and-drag onto a hotbar slot, same reasoning as above with one extra edge: the two ends of the gesture are in **different subtrees** (a `LazyVerticalGrid` cell and the row beneath it), so the drop only lands if both agree on a coordinate space. It also pins the drag against a *drifting* finger, because the grid underneath is a thousand-item scroller competing for the same hold, and a synthetic pixel-perfect dwell would never show that losing.
- `ui/ItemStackGraphic` — one item stack with vanilla's decorations (glint, durability bar, count), shared by the hotbar and the inventory grid rather than duplicated. The box maps 1:1 onto vanilla's 16×16 item area, which is what lets the decoration offsets be vanilla's own pixel numbers.
- `ui/ItemGlint` — vanilla's enchantment shimmer, drawn over an item icon. Three things make it read as the real glint rather than a coloured wash, and all three were wrong in the version it replaced: it **scrolls** (vanilla's `TextureTransform.GLINT_TEXTURING` matrix, rebuilt per frame from the wall clock — the constants are transcribed from `getGlintTransformation`), it's **masked to the item's own alpha** via an offscreen layer and `BlendMode.DstIn` so a sword glints along the blade instead of the whole 16×16 square lighting up, and it's **added** (`BlendMode.Plus`) rather than blended over, which is what stops it washing the icon out. The mod sends icons *without* glint precisely so this can animate; see its CLAUDE.md. This is also the one texture in the app drawn with `FilterQuality.Low` instead of `None` — the glint is a soft gradient whose own `.mcmeta` sets `blur`, and point-sampling it turns the shimmer into blocky steps. The frame clock is read **inside** the `Canvas` draw lambda, so an animating glint invalidates only the draw phase and never recomposes the slot.
- `ui/MinecraftGui` — the game's GUI chrome: `MinecraftButton` (nine-sliced from the socket-delivered `widget/button` sprites, labelled in the bitmap font), `Modifier.vanillaPanel()` and `Modifier.vanillaSlot()`. Used by the tab strip, the input grid, the inventory and the Settings tab's Reset/Cancel, so those are the game's controls rather than Material ones over a dirt backdrop.
  - **Every painter falls back to drawing vanilla's palette itself** when a sprite hasn't arrived, so a mod build predating the catalog keys costs appearance and not function. The panel is *always* drawn rather than sampled: vanilla has no nine-sliceable panel sprite, so its edge structure (a 1px black outline whose corners step in by two pixels, 2px white inside the top and left, 2px `#555555` inside the bottom and right, `#C6C6C6` fill) is transcribed from `gui/container/inventory.png` — read out of the 1.21.11 jar, not recalled. The fill goes down as two overlapping bands so the corner notches stay unpainted; filling the rectangle and outlining it gives a square corner with a stray pixel outside it.
  - The nine-slice border comes from each sprite's `.mcmeta` and is **not the same for all three button states** (3, 3, but 1 for `button_disabled`), and it's stored per-sprite in both source and logical pixels so a 2× resource pack doesn't come out with fat corners.
  - `MinecraftButton` carries a `contentDescription`: its label is usually a `Canvas` of bitmap glyphs, which leaves no text for a test or a screen reader to find. It also uses `indication = null` — a Material ripple over pixel art reads as a rendering fault, and the sprite swap is the press feedback.
- `ui/CreativeScreen` — the Creative tab's item picker, and the one gesture on this screen that had to be hand-rolled.
  - **`detectTapOrHoldDrag` replaced `detectDragGesturesAfterLongPress` + `clickable`, and the reason is a clock.** `awaitLongPressOrCancellation` arms a timeout on the pointer-input scope's clock and needs it to *fire while the finger sits still* — but a still finger produces no pointer events. Under `createComposeRule` that clock is driven by `advanceEventTime`, so the long press always fired and every test passed; on the Thor the timer lost the race and the first real movement went to the `LazyVerticalGrid`'s scroller, so holding an item scrolled the grid instead of lifting it. The hold is now measured from the **events' own `uptimeMillis`** and decided when the next event arrives — nothing has to fire in a vacuum, and the only moment the decision matters (the first significant movement) is itself an event. It also means the tests exercise the same quantity production does instead of a parallel one that happened to agree.
  - **The tap lives in the same detector.** The drag has to consume movement to keep the scroller out of it, and a consumed move cancels `clickable`'s pending tap anyway — two detectors racing over one finger is what produced the bug. Cost is the Material ripple, which this screen didn't want.
  - Movement up to `HOLD_SLOP_FACTOR` × touch slop is **consumed** during the hold rather than ignored, so the scroller never accumulates enough to claim the gesture from a resting thumb. Past that it really is a scroll, and the detector bails without consuming anything so the grid scrolls normally.
  - **The lift event must not also be applied as a drag delta.** It sets the drag origin to where the finger already is; adding its own travel on top throws the carried item past the finger, and the drop then misses the slot the player is plainly over. `CreativeScreenTest` caught exactly this.
  - The hotbar row's cells are **measured, not a constant** — `(maxWidth - 8 × gap) / 9`, the same arithmetic `LazyVerticalGrid` does — because a fixed height against a `weight(1f)` width only matches the grid above by coincidence, and on the Thor it didn't.
- `ui/InputGridScreen` — 3×3 grid of buttons, each pressing a key binding by id (`BIND:<id>`). **Every button is data**, driven by `InputSettings` and labelled from the mod's binding list; it used to be a hardcoded list of codes matched against a hardcoded table in the mod, and those two lists drifted (an "R" button doing an F key's job, an "L" button wired to nothing). A slot whose id the mod hasn't described — the list hasn't arrived yet, or a mod that owned it was removed — falls back to the id's last segment rather than rendering blank.

## The side-by-side container layout, kept on a branch

`feat/container-panels-side-by-side` holds the first version of the container
controls, where they sat in a **column beside the slot grid** rather than in a band
above it. It's kept deliberately, not abandoned — the layout is a judgement call
about how to spend a 1240x1080 panel, and the two are worth being able to compare
rather than argue about from memory.

What the side-by-side version got wrong, and why the band replaced it: the panel
took roughly half the width, and the grid's cell size is bound by whichever axis
runs out first. On this display that made the scale step fall from 3.95 to 3
device pixels per texture pixel (it floors to a whole pixel for bevel crispness),
so the grid came out small inside wide empty margins — while a nine-entry recipe
list had far more room than it needed. The anvil was the extreme case: its
keyboard was pinned open in the panel, so a block whose whole interaction is
"type a name and take the result" showed a half-width inventory under a keyboard
nobody was using.

Both branches carry the same mod-side commit; the layout is entirely app-side, so
`AynThorSecondScreen` has only `feat/container-panels`.

## Handoff doc vs. current code

`thor-hud-handoff.md` is accurate on protocol and overall architecture, but its file/class inventory has drifted from the current tree — don't assume a class it names still exists or is still missing without checking:

- `RadialInputPad.kt` and standalone `TiledTextureBackground.kt` / `BundledIconProvider.kt` **do not exist**. The doc's claim that a radial gesture pad is "implemented" is not reflected in the current source — only the 3×3 `InputGridScreen` grid is wired into `SecondScreenApp`. Tiling and bundled-icon-fallback logic exist but live inline inside `HudScreen.kt` and `ResourcePackIconProvider.kt` respectively, not as separate files.
- Package name is settled at `com.exojosh.minecraftsecondscreen`, not still in flux as the doc's §3 warns.

## Known unverified/fragile areas (per the handoff doc)

- (Reconnect backoff and icon-cache eviction were the entries here; both are done — see `net/ReconnectPolicy` and the LRU bound in `HudRepository`.)
- **The container decorations have not been seen on a real container yet.** The layout is pinned by `ContainerLayoutTest`/`InventoryScreenTest` and the coordinates and fill formulas are transcribed from the 1.21.11 screens' bytecode, but no capture run has yet had a furnace or brewing stand *open* — every capture so far shows the player's own handler, which has neither progress nor a title. `tools/capture_protocol.py` prints both (`progress:` and `title=`), so opening a lit furnace with the harness attached is the check. What's already confirmed on a live client: slot coordinates arrive populated, `background` resolves (armor slots report `container/slot/helmet` and friends), and all 83 catalog assets deliver with data.
- **The extras payload has not been seen on a live container.** Builds pass, 92 unit tests pass, and every one of the five new verbs was exercised against a running client — parse, dispatch, type guard, staleness check and range check all fired correctly (see the mod's CLAUDE.md for the log). What has *not* been observed is an `extras` object arriving for a real enchanting table, stonecutter, loom, villager, beacon or anvil, because opening a container needs a right-click and driving one over the socket turns out to be blocked twice over — see the mod's "Driving the game from the harness" note. Opening each block by hand with `tools/capture_protocol.py` attached is the remaining check; it prints `extras` in full.
- **Loom pattern previews are names only.** Patterns aren't items, so there's nothing for the `ICON:` path to fetch; vanilla renders those previews off a banner model. Showing them means putting a banner stack through the mod's `ItemIconRenderer`.
- **The crafter's cell toggles have a verb but no gesture.** `SLOTSTATE:` works on both sides and the `disabled` flag already greys the cell, but nothing in the Items tab sends it — picking the gesture (long-press? a fifth `MoveMode`?) is the open question rather than the plumbing.
- **Nothing can close a screen from the second display.** `CommandDispatcher` drops every `BIND:` while a screen is open, which is right for keybindings but means a player who opens a furnace can't dismiss it from the bottom screen. Would need its own verb calling `currentScreen.close()`, deliberately outside the keybinding guard for the same reason `CHAT:` is.
